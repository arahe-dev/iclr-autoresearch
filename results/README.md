# Generation-0 result ledger

The eventual `generation0.jsonl` file is append-only: one JSON object per planned run, keyed by `run_id`. The current plan is `G0-L8-SM120-EXACT-B32-C15`: 15 feasible treatments and 50 slots, retaining all 20 original CONTROL slots and the original run IDs/positions. Structurally infeasible `G0-F05` is excluded after the observed B32 warmup OOM; no F05 measurement is imputed or admitted. The original `iclr-g0-0ce16e9922b2` evidence campaign is preserved and cannot be used as a C15 output directory.

The repository contains no accepted C15 screening measurements. Its immutable champion is `908b0b1438ba038d319adf97787aac08f213b590` on `codex/champion/0000-validated-bdh-baseline`. This is the baseline identity; a later explicitly authorized campaign must pin its own clean candidate and harness commits using full 40-character SHAs. Each accepted result carries those commits and tracked-file hashes, the champion commit/branch, and the frozen plan/contract/config/canonical-source and corpus identities in `provenance`.

Use `scripts/run_generation0.py --execute` only with a separate `codex/experiment/*` or `codex/generation0/*` candidate worktree and a command that emits the complete version-2 worker protocol. Admission requires the exact oracle, same-document reset, tied-QK backward and initial-loss gates before timing, two warmups and all five B32 F+B samples with timing boundaries, a passing memory gate, and matching provenance. The runtime validator remains authoritative for hashes, relationships, timing arithmetic, and admission; the JSON schemas also constrain C15 identities and factor/arm assignments.

Both launchers require the exact device name `NVIDIA RTX PRO 6000 Blackwell Server Edition`, SM120, at least 90 GiB VRAM, and an actual CUDA UUID matching the externally selected physical GPU. Workers print their GPU/UUID and torch/CUDA identity. The supervisor streams the candidate transcript to `results/generation0_console.log` and waits for physical GPU release after every preflight and benchmark attempt, including failures and interrupts, before returning or considering another slot. Any failed process, protocol, oracle, memory, provenance, admission or release gate stops the campaign with sticky failure state; resumption requires explicit `--retry-failed`. Failed attempts never become accepted measurements.
